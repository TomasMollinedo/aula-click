# Decisiones — Aula Click

Registro corto de decisiones de arquitectura. Una decisión **tomada** no se cambia sin acuerdo del equipo; si cambia, se actualiza acá y en el doc afectado en el mismo PR. Lo que depende de una decisión **abierta** no se implementa suponiendo una respuesta (`AGENTS.md`, regla 7).

## Tomadas

| ID   | Decisión                                                                                                                                      | Por qué                                                                                                                  |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| T-01 | Next.js 16 aloja frontend y API en un solo proyecto                                                                                           | Un solo deploy y mismo origen: sin CORS ni tokens                                                                        |
| T-02 | La API es Hono + `@hono/zod-openapi`, montada en `/api/v1`                                                                                    | Contrato tipado y OpenAPI generado desde los mismos schemas que validan                                                  |
| T-03 | Better Auth va aparte, en `/api/auth`                                                                                                         | No mezclar el ciclo de autenticación con la API de negocio                                                               |
| T-04 | Prisma 7 con `@prisma/adapter-pg`                                                                                                             | Driver `pg` en lugar del engine binario clásico                                                                          |
| T-05 | Backend feature-first en capas (routes, controller, validation, service, repository); entre features solo se importan repositories            | Sin ciclos entre features y sin acoplar reglas de negocio                                                                |
| T-06 | Frontend feature-first en `src/features/<entidad>/`; `components/` solo para UI sin entidad                                                   | Todo lo de una entidad junto. Reemplaza el agrupamiento en `components/<entidad>/` de la versión anterior de `AGENTS.md` |
| T-07 | En el frontend, los datos se piden desde Client Components con TanStack Query + `fetchJson`; ningún Server Component hace `fetch` a `/api/v1` | En el servidor una URL relativa no funciona y la cookie no viaja; un solo camino de datos y un solo manejo de errores    |
| T-08 | Los schemas de Zod no se comparten entre front y back                                                                                         | El frontend no puede importar `src/server` (ESLint). Cada lado valida lo suyo; la validación que manda es la de la API   |
| T-09 | Sin `axios` ni `react-router`                                                                                                                 | Ver `dependencias.md` → Lo que no se instaló                                                                             |
| T-10 | Fechas de calendario como `@db.Date` / `YYYY-MM-DD`; horas como minutos / `HH:mm`; zona `America/Argentina/Salta`                             | Comparaciones simples y sin errores de zona horaria                                                                      |
| T-11 | Paginación por offset con respuesta `{ data, meta }`                                                                                          | Simple, suficiente para el volumen del centro                                                                            |
| T-12 | Búsqueda sin tildes con columna `busqueda` normalizada; sin `unaccent`                                                                        | `mode: 'insensitive'` no resuelve tildes y así no depende de extensiones de Postgres                                     |
| T-13 | Archivos: se guarda la clave; la subida va por multipart a la API; la lectura, con URL prefirmada (900 s)                                     | Un solo punto que conoce MinIO y URLs que no quedan viejas en la base                                                    |
| T-14 | `proxy.ts` protege todo por defecto (matcher negativo) — **A construir**                                                                      | Una sección nueva queda protegida sin acordarse de tocar el proxy                                                        |
| T-15 | Header y Sidebar se montan con `AppShell` en el layout de cada segmento de rol; el layout raíz no lleva Header                                | `/login` queda sin el esqueleto de la app autenticada                                                                    |
| T-16 | Documentación: `AGENTS.md` transversal + `docs/` por tema + `.claude/rules/` por zona                                                         | Contexto chico para las herramientas de IA y una sola fuente por tema                                                    |
| T-17 | Valores de `role`: `MESA_ENTRADAS`, `PROFESOR`, `GERENTE`, `ALUMNO`. Un usuario tiene un solo rol (antes D-01)                                | Siguen la convención de enums del dominio (`ACTIVO`, `RECURRENTE`): español, mayúsculas y guion bajo                     |
| T-18 | Los alumnos tienen usuario y portal, en el Sprint 3 (antes D-02)                                                                              | Decisión del equipo                                                                                                      |
| T-19 | Cada rol tiene un segmento real de URL: `/mesa`, `/profesor`, `/gerente`, `/portal`. No se usan route groups para separar roles (antes D-06)  | Las URLs de distintos roles no pueden chocar y el rol queda visible en la ruta                                           |

## Abiertas

Los IDs no se reutilizan: una decisión que se toma pasa a "Tomadas" con un ID nuevo y la referencia "(antes D-xx)".

| ID   | Pregunta                                                                                                                                                                                                                                                                        | Mientras tanto                                                                                                                             | Afecta a                                       |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------- |
| D-03 | Modelo de turnos recurrentes. Propuesta: guardar la regla y expandir las ocurrencias al consultar; prioridad calculada al leer                                                                                                                                                  | No se implementa la persistencia de recurrentes                                                                                            | `schema.prisma`, `turnos`                      |
| D-04 | Qué pasa al registrar un recurrente cuando alguna fecha está llena (excepciones)                                                                                                                                                                                                | Se rechaza con `BLOQUE_LLENO` y las fechas en `details`                                                                                    | `turnos`, formulario de turno                  |
| D-05 | Cómo se crea el primer gerente con `disableSignUp`. Opciones (verificar la API en la versión instalada): (a) `internalAdapter` de `auth.$context` desde el seed; (b) plugin `admin` (`createUser`), que trae su propio campo `role` y podría chocar con `additionalFields.role` | El seed no puede usar `auth.api.signUpEmail`                                                                                               | Seed, `src/lib/auth.ts`                        |
| D-07 | Tipos del frontend: escritos a mano o generados desde `/api/v1/openapi.json` (por ejemplo con `openapi-typescript`, nueva devDependency)                                                                                                                                        | Se escriben a mano en `<entidad>.types.ts`, siguiendo el OpenAPI                                                                           | `src/features/*/…types.ts`, `package.json`     |
| D-08 | Primitivos de UI: shadcn/ui o hechos a mano                                                                                                                                                                                                                                     | `components/ui/` a mano, con la misma API que tendría shadcn/ui                                                                            | `src/components/ui/`, `package.json`           |
| D-09 | Tests de frontend: si hay y con qué (Vitest + Testing Library + jsdom serían dependencias nuevas)                                                                                                                                                                               | Los tests automatizados cubren services y `shared/` del backend                                                                            | `vitest.config.mts`, `package.json`, CI        |
| D-10 | Cómo se vincula la cuenta (usuario de Better Auth) con el registro de dominio de profesores y alumnos, y quién crea esas cuentas                                                                                                                                                | Los usuarios los crea un gerente; el schema no tiene la relación. Resolver antes de las pantallas del rol profesor y del portal (Sprint 3) | `schema.prisma`, `profesores`, `alumnos`, seed |
